I used Claude Code as a reading assistant throughout this project, not as a bug finder. The workflow that actually worked was: read the code myself → ask the AI to explain or contrast something specific → verify the answer against the source before acting on it.

Where it genuinely helped:

- **Orientation.** After cloning, I had it summarize what each file in `services/` was responsible for and how `routes/` connected to it. That produced the skeleton of the codebase map below in a few minutes instead of half an hour of clicking through files.
- **Contrasting two code paths.** For the notification issue, I pasted `add_to_playlist()` and `rate_song()` side by side and asked what the structural difference between them was. Phrasing it as "compare these two blocks" rather than "what's broken here" was the thing that made it useful — it described the shape of the difference (one function ends with a `create_notification()` call, the other ends at `db.session.commit()`) and let me draw the conclusion.
- **Python date semantics.** I asked it to confirm the difference between `datetime.weekday()` and `isoweekday()`, and specifically which integer Sunday maps to in each. I already suspected the streak comparison was the problem; I wanted the numbering confirmed rather than guessed.
- **SQL join semantics.** I asked why a join against an association table changes the row count of a `SELECT`, which confirmed the row-multiplication reasoning in Issue #3.

Where I had to correct it or do the work myself:

- Asked cold, without having read the files, it was happy to speculate about plausible-sounding causes that weren't the actual ones. The explanations only became reliable once I'd found the suspicious code first and asked a narrow question about it. This matches the project's warning, and it's the main thing I'd carry forward.
- For Issue #2 it initially framed the problem as a timezone bug. Reading `feed_service.py` showed the timezone handling is consistent (everything is UTC-aware); the real mismatch is between a rolling-window cutoff and a calendar-day feature. I had to override that framing.
- For Issue #5 it suggested the ordering was wrong before I pointed it at the actual return statement. The `order_by` is correct; the slice on the return line is what drops a row.
- Every diagnosis below was confirmed by reading the function and checking it against the docstring that function already publishes. Several of these bugs are only visible as bugs because the code contradicts its own documented contract — that's a judgment the AI could not make for me.

## Codebase Map

Written before opening any issue. This describes how the app is put together.

### Top level

- **`app.py`** — Flask application factory. Creates the `SQLAlchemy` object (`db`) that every other module imports, reads `DATABASE_URL` from the environment (defaulting to `sqlite:///mixtape.db`), registers the four blueprints under their URL prefixes (`/songs`, `/playlists`, `/users`, `/feed`), and calls `db.create_all()` inside an app context. `db` lives here rather than in `models.py`, which is why `models.py` starts with `from app import db` — the import direction is app → models, not the reverse.
- **`models.py`** — All seven SQLAlchemy models plus three association tables.
  - Models: `User`, `Tag`, `Song`, `ListeningEvent`, `Rating`, `Playlist`, `Notification`. Every primary key is a UUID string generated by `generate_uuid()`.
  - Association tables: `friendships` (self-referential user↔user, stored as two rows per friendship so the relationship is symmetric in both directions), `song_tags` (song↔tag), and `playlist_entries`.
  - `playlist_entries` is the richest of the three: besides the two foreign keys it carries `position` (integer, not null), `added_by`, and `added_at`. So playlist membership has an explicit ordering column rather than relying on insertion order.
  - `User.listening_streak` and `User.last_listened_at` are denormalized onto the user row — the streak is a stored counter that gets mutated on each listen, not something recomputed from `ListeningEvent` history.
  - `Rating` has a `UniqueConstraint` on `(user_id, song_id)`, so a user has at most one rating per song; re-rating must be an update, not an insert.
  - Most models expose `to_dict()`, which is what the routes serialize.
- **`seed_data.py`** — Drops and recreates all tables, then populates 5 users with friendships, 25 songs deliberately spread across 0-tag / 1-tag / 3-tag groups, 3 playlists, listening events at a mix of ages, and one pre-existing notification.
- **`tests/`** — Three pytest modules (`test_streaks.py`, `test_search.py`, `test_playlists.py`). Each defines its own `app` fixture building an in-memory SQLite database via `create_app({"TESTING": True, "SQLALCHEMY_DATABASE_URI": "sqlite:///:memory:"})`, so tests touch the service functions directly rather than going over HTTP. There is no shared `conftest.py`; the fixture is duplicated per module.

### The layering pattern

The app is consistently two-layered, and the split is strict:

- **`routes/`** does HTTP work only — pull values off `request.args` or `request.get_json()`, check required fields are present, call exactly one service function, and wrap the result in `jsonify()`. The routes also own the error-to-status-code mapping: nearly every route wraps its service call in `try/except ValueError` and converts the exception into a 400 or 404.
- **`services/`** owns all business logic and all database access. Services raise `ValueError` for "not found" and validation failures and otherwise return plain dicts or model instances. No service imports Flask.

A consequence worth noting: because services signal failure by raising `ValueError` and routes translate that into a status code, the HTTP contract is defined jointly by the two layers, and a service that returns a wrong *value* (rather than raising) will surface as a perfectly successful `200` response with wrong content.

### Service responsibilities

- **`streak_service.py`** — `record_listening_event()` writes a `ListeningEvent` and then calls `update_listening_streak()`, which mutates the counter on the `User` row based on how many calendar days separate `user.last_listened_at` from now. `get_streak()` just reads the stored integer back.
- **`feed_service.py`** — `get_friends_listening_now()` resolves the user's friend IDs, selects their `ListeningEvent` rows newer than a cutoff derived from the module-level `RECENT_THRESHOLD`, orders them newest-first, then walks the ordered list keeping only the first event per friend. `get_activity_feed()` is the unfiltered sibling — same friend lookup and ordering, no recency cutoff, just a `limit`.
- **`search_service.py`** — `search_songs()` runs a single `select(Song)` with an outer join onto `song_tags` and an `ilike` OR-filter across `title` and `artist`. `get_song()` is a plain primary-key lookup. Note that tag names reach the response through `Song.to_dict()`, which reads `self.tags` — a relationship configured with `lazy="subquery"` in `models.py` and therefore loaded independently of anything the search query joins.
- **`notification_service.py`** — Holds both notification plumbing (`create_notification()`, `get_notifications()`, `mark_as_read()`) and two user actions that are notification-adjacent: `add_to_playlist()` and `rate_song()`. `add_to_playlist()` appends to `playlist.songs`, commits, then calls `create_notification()` targeting `song.shared_by`, guarded by a check that the actor isn't the sharer. `rate_song()` validates the 1–5 range, looks up the song and the rater, then either updates an existing `Rating` row or inserts a new one, and commits.
- **`playlist_service.py`** — `create_playlist()` inserts a row; `get_playlist_songs()` joins `Song` against `playlist_entries`, filters to the playlist, orders by `playlist_entries.c.position` ascending, and returns serialized dicts; `get_playlist()` and `get_user_playlists()` are plain lookups.

### Data flow: a user rates a song

`POST /songs/<song_id>/rate` with a JSON body of `{"user_id": ..., "score": ...}`.

1. `routes/songs.py::rate()` receives the request, reads `user_id` and `score` off the parsed JSON, and short-circuits with a 400 if either is missing.
2. It calls `notification_service.rate_song(user_id, song_id, int(score))` inside a `try`.
3. `rate_song()` validates `1 <= score <= 5`, raising `ValueError` otherwise. It loads the `Song` and the rating `User` via `db.session.get()`, raising `ValueError` if either is absent.
4. It queries `Rating` filtered by `(user_id, song_id)`. If a row exists it overwrites `score` in place; if not it constructs a new `Rating` and adds it to the session. This branch is what honours the `unique_user_song_rating` constraint.
5. `db.session.commit()` persists, and the `Rating` instance is returned up to the route.
6. The route serializes it with `to_dict()` and returns `201`.

Any `ValueError` raised anywhere in steps 3–4 unwinds to the route's `except` and becomes a `400` with the exception text as the error body.

### Data flow: viewing a playlist

`GET /playlists/<playlist_id>/songs` → `routes/playlists.py::get_songs()` → `playlist_service.get_playlist_songs()`. The service resolves the `Playlist` (404 via `ValueError` if missing), then issues a join query against `playlist_entries` ordered by `position`, and returns a list of song dicts. The route wraps that list as `{"songs": [...], "count": len(songs)}`, so the `count` field is derived from the returned list rather than from a separate count of playlist membership.

## Root Cause Analyses

### **Issue #1 — My listening streak keeps resetting**

**How I reproduced it**

The report had an unusually specific clue — it happened twice, and both times on a Sunday — so the reproduction needed to control the calendar day rather than just the gap between listens. The repo already ships a test that does exactly this, `tests/test_streaks.py::test_streak_increments_on_sunday`, which calls `update_listening_streak()` with a fixed Saturday (`2024-06-15`) and then a fixed Sunday (`2024-06-16`) and asserts the streak reaches 2. Running `pytest tests/test_streaks.py` on the unmodified checkout fails that case with the streak at 1 while the four neighbouring cases (new user, consecutive weekday, same-day double listen, skipped day) all pass. That pattern — consecutive days increments fine on a Tuesday, resets on a Sunday — is kenji's report reproduced deterministically, without waiting for an actual Sunday.

**How I found the root cause**

I traced from the endpoint named in the report. `GET /users/<id>/streak` lands in `routes/users.py::streak()`, which calls `streak_service.get_streak()` — but that function only reads `user.listening_streak` back, so it could not be where the value was destroyed. That told me the corruption happened on the *write* path, not the read path, so I followed the other entry point into the same service: `POST /songs/<id>/listen` → `routes/songs.py::listen()` → `record_listening_event()` → `update_listening_streak()`.

`update_listening_streak()` is short, and its docstring states the rules plainly: increment when the user listened yesterday, reset only when more than one day has passed. Reading the branch that implements those rules against the docstring directly above it was the moment it was obvious — the increment branch carries a second condition that the documented rules never mention.

**The root cause**

The increment branch read `elif days_since_last == 1 and today.weekday() != 6:`. `days_since_last == 1` is the correct and sufficient test for "listened yesterday." The extra `today.weekday() != 6` clause adds a requirement that today must not be Sunday, because Python's `datetime.weekday()` numbers Monday as 0 through Sunday as 6.

The damage comes from what the condition falls through to. The branch is an `elif` in a three-way chain ending in a bare `else` that sets the streak to 1. So on a Sunday a user who listened yesterday fails the increment test and lands in the reset branch — the same branch that exists to handle genuinely skipped days. The code cannot distinguish "you listened yesterday but today is Sunday" from "you missed a day," and treats the first as the second. That is why kenji's streak went to 1 rather than simply failing to advance from 12, and why Monday's listen moved it to 2: by then `last_listened_at` was Sunday, `days_since_last` was 1, Monday is not day 6, so the increment branch ran normally against a counter that had already been reset.

**My fix**

Removed the `and today.weekday() != 6` clause so the branch reads `elif days_since_last == 1:`. One line, and it restores the condition to exactly what the function's own docstring specifies. No other logic needed to change — the same-day no-op branch and the reset branch were both already correct, and the day-of-week check was the only thing standing between them and the documented behaviour.

**My side-effect check**

The concern with touching a three-way branch is breaking the cases that were working, so I checked each of the other documented rules still holds. The remaining tests in `tests/test_streaks.py` cover them directly: a first-time listener still starts at 1 (that path returns early, before the branch I edited), listening twice in one day still leaves the streak unchanged (`days_since_last == 0` returns before reaching the `elif`), and skipping a day still resets to 1 (`days_since_last == 2` fails the `elif` and falls to the `else`, which is now the only way to reach it). I also specifically checked the Saturday→Sunday and Sunday→Monday transitions, since the fix changes behaviour on both sides of that boundary — the condition is now purely a function of the day gap, so neither direction can special-case itself any more.

### **Issue #2 — Friends Listening Now shows people from yesterday**

**How I reproduced it**

The detail that makes this reproducible is in the timings rather than the data: nova checked at 9am and saw a listen from 11pm the night before — a gap of about ten hours. Any fixed-duration window longer than ten hours will show that event, so the reproduction is to create a `ListeningEvent` for a friend timestamped late on the previous calendar day and then call `get_friends_listening_now()` as if it were the following morning. The event comes back in the feed even though it did not happen today. The complementary half of the reproduction is what makes the shape unmistakable: take that same event and query it at, say, 11:30pm the following night instead, and it has disappeared — not because the calendar rolled over, but because 24 hours elapsed. The entry's lifetime tracks the clock, not the day. I added `tests/test_feed.py` to pin both halves down (see the regression test section).

**How I found the root cause**

`GET /feed/<user_id>/listening-now` → `routes/feed.py::listening_now()` → `feed_service.get_friends_listening_now()`. The service does three things — resolve friend IDs, filter events by a cutoff, deduplicate to one event per friend — and only the second could produce "too old" entries, so that is where I looked.

What made me confident was comparing the filter against the feature it serves rather than against some notion of correct time handling. The cutoff was computed as `datetime.now(timezone.utc) - RECENT_THRESHOLD`, with `RECENT_THRESHOLD = timedelta(hours=24)` defined at module scope. That is a correct implementation of "in the last 24 hours." The feature, per its name and per the reported expectation, is "today." Those two are different specifications that happen to agree for most of the day and diverge exactly at the boundary the user noticed.

I briefly suspected timezone handling instead, since mixing naive and aware datetimes is a common source of this symptom. Reading the module ruled that out: `datetime.now(timezone.utc)` is UTC-aware and the stored `listened_at` values are written UTC-aware too, so the comparison is consistent. The mismatch is semantic, not arithmetic.

**The root cause**

`get_friends_listening_now()` filtered on a rolling window anchored to the moment of the request — `now - 24 hours` — rather than on a calendar-day boundary. A rolling window has no notion of "yesterday"; it only knows elapsed time. So an event at 11pm stays inside the window until 11pm the next day, which is precisely the behaviour nova described: "stuff from yesterday evening keeps hanging around in the feed until the same time the next day." Every entry in the feed got a 24-hour lifetime starting from when it happened, and because each event carries its own timestamp, each one expired at a different moment rather than all of them clearing together at midnight.

The deduplication step downstream then made the stale data more prominent rather than less. It keeps the single most recent event per friend, so for a friend whose only activity was last night, the stale event is not merely present in a long list — it is that friend's entire representation in the feed, labelled as what they are listening to now.

**My fix**

Replaced the rolling cutoff with the start of the current UTC day: `cutoff = now.replace(hour=0, minute=0, second=0, microsecond=0)`. The filter and ordering around it are untouched, so the query shape is the same — only the anchor moved from "24 hours before this request" to "midnight at the start of today."

This fixes the root cause rather than the symptom because the failure was never that the window was the wrong *length*; shortening `RECENT_THRESHOLD` to, say, 12 hours would still have left entries expiring on a rolling schedule and would have introduced a new wrong answer (a friend who listened at 8am would vanish by 8pm the same day, while still being someone who listened today). Anchoring to midnight makes the window mean the same thing the feature name means, and makes the whole feed turn over at once at the day boundary.

I also removed the now-unused `RECENT_THRESHOLD` constant and the `timedelta` import it needed, so the module does not carry a dead constant that still looks like the feed's configuration, and I updated the function's docstring to state the calendar-day semantics explicitly so the next reader has the contract written down.

**My side-effect check**

`get_activity_feed()` is the other function in the module and shares the friend-resolution and ordering logic, so I checked it was unaffected: it never referenced `RECENT_THRESHOLD`, applying a `limit` instead of a recency filter, which its docstring already called out as the deliberate difference between the two functions. Removing the constant therefore could not change it, and I confirmed no other module imported `RECENT_THRESHOLD` before deleting it. I also verified the deduplication loop still behaves correctly against a smaller result set, including the case where filtering removes every event for a friend — that friend simply no longer appears, which is the intended outcome — and the case of a user with no friends at all, which still returns early with an empty list.

### **Issue #3 — The same song keeps showing up twice in search**

**How I reproduced it**

The report contains the key to this one: *some* songs duplicate and others do not, and the specific song named — *Crown Heights Anthem* — comes back three times. So the reproduction is not "search and count" in general, it is searching for songs that differ in one particular property. `seed_data.py` turns out to group its songs into exactly three buckets with a comment marking the third as the relevant one: three songs with no tags, five with one tag, and five with three tags each, *Crown Heights Anthem* among them.

Searching for a no-tag song returns one row, a one-tag song returns one row, and a three-tag song returns three identical rows. The multiplier is the tag count: a song appears once per tag it carries, and a song with no tags still appears once. `tests/test_search.py` already encodes this as three separate cases across the three buckets, and on the unmodified checkout only the multi-tag case fails.

**How I found the root cause**

`GET /songs/search?q=...` → `routes/songs.py::search()` → `search_service.search_songs()`. The route only forwards `q` and wraps the result with a `count` derived from the list length, so it could not be inventing rows; the duplication had to come from the query itself.

`search_songs()` builds a single statement: `select(Song)`, an `outerjoin` onto the `song_tags` association table, and an `ilike` OR-filter over `title` and `artist`. Once I had the tag-count correlation from the reproduction, the join was the obvious suspect, and the mechanism is standard SQL rather than anything specific to this app: joining a one-to-many produces one result row per match on the many side. A song with three `song_tags` rows therefore yields three rows, each carrying the same `Song`. `.scalars()` then extracts the `Song` from each row, producing the same object three times, and `.all()` returns the list with the repeats intact — `scalars()` unwraps rows, it does not deduplicate them.

What settled it was checking whether the join was earning its place. The filter references only `Song.title` and `Song.artist` — nothing from `song_tags`. And the tag names in the response do not come from the join either: they come from `Song.to_dict()`, which reads `self.tags`, a relationship declared in `models.py` with `lazy="subquery"` and therefore loaded by its own separate query whenever the attribute is touched. So the join contributed nothing to either the filtering or the output. Its only effect on the result was the duplication.

**The root cause**

The query outer-joined `song_tags` without restricting the result to distinct songs. Because the relationship between a song and its tags is one-to-many, the join multiplied each matching song into one row per tag, and the pipeline preserved those duplicates all the way to the response.

The reason the symptom looked inconsistent to the reporter is that the multiplier is per-song: the row count equals the song's tag count, with the outer join guaranteeing a floor of one so untagged songs still appear exactly once. Songs with one tag are indistinguishable from correct behaviour, which is why only certain songs looked broken while others seemed fine.

**My fix**

Removed the `outerjoin` from the statement, leaving `select(Song).filter(...)`. Each matching song now produces exactly one row.

I chose this over adding `.distinct()` deliberately. `.distinct()` would also have produced the right list, but it treats the symptom: the database would still build the multiplied result set and then collapse it, and the join would remain in the code looking as though the query depended on it. Since the join contributes to neither the filter nor the returned tag data, deleting it addresses why the duplicate rows existed in the first place and leaves a query whose shape matches what it actually needs. I also removed the `song_tags` and `Tag` imports, which this change left unused, and noted the one-row-per-song guarantee in the docstring.

**My side-effect check**

The thing worth verifying after deleting a join is that the data it appeared to supply is still present, so I checked that search results still include tag names. They do — `tags` is populated by `Song.to_dict()` through the `lazy="subquery"` relationship, on a path that never involved this query. A song with three tags still reports all three in its `tags` list; it simply does so once instead of three times. I confirmed the untagged and single-tag cases are unchanged, since those are the ones that looked correct before and could regress silently, and that a query matching nothing still returns an empty list rather than erroring. I also checked `get_song()`, the other function in the module, which does a primary-key lookup and never referenced the imports I removed.

### **Issue #4 — I got notified when a friend added my song to a playlist but not when they rated it**

**How I reproduced it**

aaliya's report conveniently includes its own control case, so I reproduced both halves against the same pair of users. Have one user add another's shared song to a playlist, then read `GET /users/<sharer_id>/notifications`: a `song_added_to_playlist` entry is there. Then have the same user rate a different song shared by the same person via `POST /songs/<song_id>/rate`, and read the notifications again: the list is unchanged.

The second observation is what makes this precise rather than a vague "notifications are flaky." The rating itself succeeds — the endpoint returns `201`, and fetching the song back shows the rating persisted. So the write path works and only the notification is absent. That rules out a failed request or a rolled-back transaction and points at something the rating path simply never does. It also matches the reporter's note that this affects everyone she asked, rather than being specific to her account or one song.

**How I found the root cause**

The hint that the cause is architectural rather than a typo shaped how I read this. Both actions live in the same file, `services/notification_service.py`, which is the natural place to compare them, so I read `add_to_playlist()` and `rate_song()` against each other line by line.

They are near-identical in structure. Both load the target `Song` and the acting `User` with `db.session.get()` and raise `ValueError` if either is missing. Both mutate state — one appends to `playlist.songs`, the other updates or inserts a `Rating`. Both call `db.session.commit()`. Then they diverge: `add_to_playlist()` continues past the commit into a guarded notification block, checking `if song.shared_by != added_by_user_id:` and calling `create_notification()` with a type of `song_added_to_playlist`. `rate_song()` commits and returns.

Two further things confirmed this was an omission rather than a deliberate design choice. First, `create_notification()`'s own docstring documents its `notification_type` parameter as "a short type string, e.g. `'song_added_to_playlist'` or `'song_rated'`" — the module already names the event type that nothing in the codebase ever creates. Second, `get_notifications()` applies no filtering by type, so a `song_rated` row would be returned to the user if one existed. The retrieval side was ready for a notification the creation side never produced.

**The root cause**

`rate_song()` never called `create_notification()`. The function performed its own job correctly — validating the score, honouring the one-rating-per-user-per-song constraint by updating in place when a row already existed, and committing — but the notification side effect that the sibling action performs was simply absent from it.

So this is not a bug in the notification machinery. `create_notification()` works, which is why playlist-add notifications arrive reliably, and the storage and retrieval paths are type-agnostic. The failure is that one of the two user actions that should emit a notification was never wired to the mechanism, leaving an inconsistency between two operations that the module otherwise treats as parallel. That is also why no error ever surfaced: nothing failed, a step just never happened.

**My fix**

Added a notification block to `rate_song()` after the commit, mirroring the one in `add_to_playlist()`: the same `if song.shared_by != <actor_id>:` guard so people are not notified about their own ratings, a call to `create_notification()` targeting `song.shared_by`, and the `song_rated` type the module's documentation already specified. The body follows the phrasing of the existing message — `"{rater.username} rated your song '{song.title}' {score} stars."` — with the noun singularised for a score of 1 so a one-star rating does not read "1 stars."

Placing the call after `db.session.commit()` is deliberate and matches the sibling: the rating is durable before any notification is emitted, so a failure in notification creation cannot leave a user notified about a rating that was not saved. I also updated the function's docstring, which previously described only the saving half of its job.

**My side-effect check**

The risk in adding a side effect to an existing function is firing it when it should not fire, so I checked the paths where it must stay silent. A user rating their own shared song produces no notification, because the `song.shared_by != user_id` guard short-circuits exactly as it does for playlist adds. Invalid input is unaffected: an out-of-range score and a missing song or user all raise `ValueError` before the commit, so no notification is created for a rating that never happened, and the route still converts those into a `400`.

I paid particular attention to re-rating, since the `unique_user_song_rating` constraint makes it a distinct path. Changing an existing rating updates the row in place and now also emits a notification — which I believe is right, since the sharer should learn their song was re-rated, and it matches the reporter's expectation that a rating produces a notification "same as for the playlist add." It does mean repeated re-rating produces repeated notifications; `add_to_playlist()` has the same property via its `if song not in playlist.songs` guard, so the two remain consistent with each other. Finally I confirmed `add_to_playlist()` itself is untouched and still produces its notification, and that `get_notifications()` returns both types together ordered by recency, since it filters only on `user_id` and optionally `read`.

### **Issue #5 — The last song in a playlist never shows up**

**How I reproduced it**

darius described a self-correcting symptom, which is the most informative part of the report: the missing song reappears when someone adds a new one, and the new one goes missing instead. So the reproduction has to be a sequence, not a single read.

Fetch a playlist's songs via `GET /playlists/<id>/songs` and compare the returned `count` against the number of `playlist_entries` rows for that playlist — the response is short by exactly one, and the absent song is the one with the highest `position`. Then add another song and re-fetch: the previously missing song is now present, and the newly added one is absent. The deficit stays at exactly one no matter how many songs are added, and it is always the last by position. `tests/test_playlists.py::test_playlist_returns_all_songs` captures the static half of this, seeding five songs and asserting five come back; on the unmodified checkout it reports four.

An empty playlist was worth checking separately during reproduction, because "always one short" and "returns nothing" are indistinguishable when the correct answer is zero.

**How I found the root cause**

`GET /playlists/<playlist_id>/songs` → `routes/playlists.py::get_songs()` → `playlist_service.get_playlist_songs()`. The route is a thin wrapper that builds `{"songs": songs, "count": len(songs)}` from whatever the service hands back, and since `count` is derived from the list rather than counted independently, the route reports the deficit faithfully rather than causing it.

My first assumption was that the ordering was wrong, since "the last one" is a positional description. Reading the query ruled that out: it joins `Song` against `playlist_entries`, filters on `playlist_id`, and orders by `playlist_entries.c.position` ascending, which is correct — `position` is a not-null column on the association table, so playlist order is explicit rather than incidental, and the fetched rows were complete.

That left the return statement, which is where the row disappears: `return [song.to_dict() for song in songs[:-1]]`. The `[:-1]` slice drops the final element of an already-correct, already-ordered list. Seeing it directly under a docstring that promises the opposite is what made it certain rather than suspicious.

**The root cause**

`get_playlist_songs()` sliced its result with `[:-1]` before serializing, discarding the last element of the ordered list. Because the query sorts by `position` ascending, the last element is the highest-positioned entry — the most recently added song — which is exactly the song users reported missing.

This also explains the behaviour that made the bug look stranger than it is. The slice is relative to the current result, not tied to any particular song, so adding a new entry gives it the highest position, making it the new last element and therefore the new casualty. The previously hidden song moves up one place and becomes visible. The playlist is not hiding a specific song; it is always hiding whichever song is currently last.

The function's own docstring states the contract it breaks twice over: "Songs are returned in the order they were added," and, under a `Note:`, "This function returns all songs in the playlist." The ordering half was honoured and the completeness half was not.

**My fix**

Removed the slice so the return reads `return [song.to_dict() for song in songs]`. Nothing else changed — the query, the filter, and the `order_by` were all already correct, and the only defect was the truncation applied to their result.

**My side-effect check**

Because the route derives `count` from the returned list, the fix corrects the reported count automatically, and I confirmed it now matches the number of `playlist_entries` rows for the playlist. I checked ordering is preserved, since my change touches the same expression that produces the final list: songs still come back ascending by `position`, which `test_playlist_returns_songs_in_order` asserts by exact title sequence.

The boundary case I was most concerned about was the empty playlist, since `[][:-1]` is `[]` and a slice bug is invisible there — a playlist with no songs still returns an empty list rather than erroring, so removing the slice did not change behaviour in the one case where the old code was accidentally right. I also checked the single-song playlist, which is where the old code was most destructive (it returned nothing at all) and which now correctly returns that one song. The other functions in the module, `get_playlist()` and `get_user_playlists()`, do not go through this code path and are unaffected; `add_to_playlist()` in `notification_service.py` imports `get_playlist_songs` but does not call it, so nothing downstream depended on the truncated list.
